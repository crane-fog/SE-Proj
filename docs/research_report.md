# 需求调研报告

## 1. 干系人分析

### 1.1 内部用户角色

| 角色名称             | 角色定位             | 核心职责与诉求                                               | 权限边界                                                             |
| :------------------- | :------------------- | :----------------------------------------------------------- | :------------------------------------------------------------------- |
| Admin（管理员）      | 服务器与系统所有者   | 保证服务器资产与凭据安全，控制高危操作风险，及时接收异常告警 | 拥有节点 SSH 密钥管理、大模型配置、用户角色分配及其余所有权限        |
| Operator（运维员）   | 日常运维与开发协作者 | 编写期望状态基线，借助智能体快速定位故障并复用历史解决方案   | 可管理 YAML 基线、发起交互式排障对话、维护长期记忆                   |
| Viewer（只读审计员） | 协作者或审计观察员   | 掌握服务健康状况与故障处置记录，辅助核查系统稳定性           | 仅具备只读查看权限，可浏览健康面板、诊断轨迹与记忆库，禁止任何写操作 |

### 1.2 外部系统

1. 受管 Linux 节点（SSH Server）：提供标准 SSH 服务，承载主机资源。
2. OpenAI compatible 大模型接口：提供大模型推理能力，支撑故障诊断主体功能。
3. Prometheus：定时抓取控制面暴露的 /metrics 指标，触发 Alertmanager 告警规则并向外部渠道推送消息。

## 2. 业务目标与现状痛点

### 2.1 现状痛点

1. 运维工具两极分化：企业级监控与自动化平台部署繁重，个人与小型团队配置成本过高；纯手动 SSH 排障则面临重复劳动多、排障过程不可追溯的问题。
2. 运维经验随时间流失：个人开发者在数月后再次遭遇相同的容器异常退出或磁盘占满问题时，往往遗忘此前使用的排查命令与临时修复脚本。
3. 大模型直接执行风险高：通用对话式 AI 缺乏只读隔离、命令安全审查与凭据脱敏机制，直接用于生产或个人主机运维存在误删数据与泄露密钥的风险。

### 2.2 业务目标

1. 构建零目标端代理、单二进制部署的轻量级运维控制面，降低部署与纳管门槛。
2. 结合确定性基线探测与智能体只读根因诊断，实现故障快速定位与历史经验沉淀。
3. 接入 Prometheus 指标与 Alertmanager 消息推送，保障异常状态及时触达，并保证大模型故障时基础监控降级可用。

## 3. 竞品对比分析

| 对比产品    | 核心能力                       | 在个人/小团队场景的局限                                      | 本项目差异化优势                                             |
| :---------- | :----------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| Ansible     | 声明式配置与无代理执行能力成熟 | 规则完全静态，缺乏运行时异常根因推理与经验记忆能力           | 结合声明式基线检查与大模型动态根因诊断，并沉淀自适应长期记忆 |
| Claude Code | 代码分析与终端工具调用能力强   | 面向单机编程任务，缺乏多节点定时探测、审批流与持久化运维记忆 | 原生支持多节点 SSH 定时巡检、三角色权限隔离与人机协同审批    |
| Datadog     | 指标、日志与链路可观测性全面   | 架构重、资源占用高且商业授权成本高，不适合个人及实验室规模   | 控制面单文件轻量部署，集成标准 Prometheus 接口，成本可控     |

## 4. 访谈纪要

### 访谈记录 1：实验室服务器管理员

- 访谈方式：线上文字
- 现状与痛点摘要：同时维护多台实验室 Linux 服务器，缺乏轻量级的标准化批量巡检与基线核查方案。

### 访谈记录 2：个人开发者

- 访谈方式：线下交流
- 现状与痛点摘要：尝试借助通用大模型辅助服务器排障，但担忧模型生成破坏性 shell 命令误改系统状态，同时也担心环境变量与配置文件中的密钥信息外泄。

### 访谈记录 3：个人开发者

- 访谈方式：线下交流
- 现状与痛点摘要：独立维护多个云主机与容器服务时，间隔数月再次遭遇同类容器异常退出、证书过期或端口冲突问题，往往遗忘上次排查命令与修复步骤，需要反复检索资料或重新提问，耗时较多。

### 访谈记录 4：项目协作者

- 访谈方式：线上文字
- 现状与痛点摘要：在小组协作开发场景下，仅管理员掌握服务器登录凭据与历史操作信息，其他协作者无法实时了解服务器当前运行状态与近期运维变更，每次核查均需口头询问管理员，信息同步滞后。
